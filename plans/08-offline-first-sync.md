# План 8. Offline-first синхронизация заметок

Статус: проект; перед реализацией требуется решение ADR-006 из этапа 0.
Приоритет: высокий для мобильного клиента; не блокирует текущий План 7
«Автосохранение».
Зависимости: План 1 (готов: actor, optimistic locking, история), План 2
(готов: ACL). Если Git-ревизии должны фиксировать sync-операции, сначала
завершить Plan 9. Архитектурное обоснование —
[notes-sync-system-design.md](../docs/notes-sync-system-design.md).

## 1. Цель

Дать пользователю модель Apple Notes: изменения сначала надёжно сохраняются
на текущем устройстве, затем автоматически доходят до сервера и остальных
устройств. Web — первый клиент; протокол должен позволить позднее написать
iOS-клиент на SQLite без изменения API или семантики синхронизации.

Пользовательские инварианты:

1. Потеря сети, закрытие вкладки или перезагрузка не теряют уже показанную
   как сохранённую локально правку.
2. Серверное подтверждение означает, что изменение переживёт удаление
   локальных данных и будет видно другим устройствам.
3. Повтор `push`, пропуск WebSocket-события и reconnect не создают дублей и
   не приводят к расхождению.
4. ACL ограничивает sync так же, как прямое чтение/запись заметок.

## 2. Границы

### В первом релизе

- один пользователь на нескольких его устройствах;
- Markdown-заметки, создание, изменение, перемещение и удаление;
- local cache в IndexedDB, durable outbox, `push`/`pull` и live-сигнал;
- понятный статус «Сохранено на устройстве» / «Синхронизировано» / «Ошибка»;
- optimistic revision и явный конфликт (`409`) как временная стратегия
  параллельного редактирования;
- серверная история и ACL сохраняют нынешнюю семантику.

### Не входит

- CRDT/совместное редактирование текста, E2EE, sharing между аккаунтами;
- офлайн-загрузка вложений, фоновая iOS-синхронизация;
- двусторонний импорт произвольных изменений файлов в vault;
- переход всего приложения на PostgreSQL.

CRDT, sharing и E2EE — самостоятельные последующие планы. Не добавлять
зависимость от Yjs/Automerge в первом релизе.

## 3. Важное архитектурное решение

Текущий продукт — файловый vault: Markdown является источником истины,
watcher видит и внешние изменения. Полная замена его PostgreSQL, как в общем
system design, — отдельная миграция и не является неявной частью этой работы.

Для первого релиза сервер остаётся vault-first. Рядом с vault появляется
служебное хранилище sync-метаданных (по умолчанию SQLite в `/data`, не в
vault и не в git-истории): журнал подтверждённых операций, монотонный
`account_seq`, дедупликация `op_id` и transactional outbox. Markdown-файл
остаётся материализованным представлением заметки.

Последствие: внешнее изменение Markdown-файла не содержит `op_id`. Watcher
создаёт серверную change-запись `source: filesystem` с новым курсором;
клиенты получают её через `pull`. Внешние изменения, сделанные одновременно
с офлайн-клиентом, используют существующий `baseHash` и могут вернуть 409.
Это честнее, чем тихо перезаписать файл.

## 4. Этап 0 — ADR и исследование кода

До первой строки production-кода агент создаёт `docs/adr/0006-sync-journal.md`
и подтверждает:

- расположение БД: новый параметр `sync.dataFile`, Docker default
  `/data/sync.db`; запрет хранить её в vault;
- SQLite driver, миграции и один writer/транзакции; отсутствие сетевой БД в
  MVP;
- представление пути: canonical vault-relative path, нормализованный как в
  `filesystem`, без абсолютных путей;
- порядок: `account_seq` общий для vault (в текущей single-vault модели),
  строго возрастающий только на сервере;
- поведение watcher для внешних файловых изменений и запрет циклических
  событий от собственных sync-записей;
- retention tombstone: 30 дней; физический purge остаётся задачей Plan 3;
- компромисс конфликтов: версия файла/hash вместо CRDT.

Если в исследовании окажется, что текущий watcher нельзя надёжно отличить от
собственной записи, остановиться после ADR и предложить минимальный механизм
origin marker/подавления событий, не гадать.

## 5. Модель данных и контракты

### 5.1. Сервер

```text
sync_operations(
  op_id TEXT PRIMARY KEY, actor TEXT NOT NULL, device_id TEXT NOT NULL,
  path TEXT NOT NULL, kind TEXT NOT NULL, payload JSON NOT NULL,
  base_hash TEXT, account_seq INTEGER UNIQUE NOT NULL,
  created_at TIMESTAMP NOT NULL
)
sync_outbox(account_seq INTEGER PRIMARY KEY, event JSON NOT NULL, published_at TIMESTAMP NULL)
sync_devices(actor TEXT, device_id TEXT, last_cursor INTEGER, last_seen_at TIMESTAMP,
             PRIMARY KEY(actor, device_id))
```

`op_id` — UUID клиента; сервер дедуплицирует именно его. Операция и изменение
файла выполняются под существующим path lock. В одной транзакции sync-БД
записываются operation, новый `account_seq` и outbox-event. Затем publisher
доставляет событие в WebSocket. Если процесс упал до публикации, event остаётся
и будет доставлен после рестарта.

Ограничение: запись Markdown и SQLite не могут быть одной атомарной
транзакцией. Нужно выбрать и задокументировать recovery-процедуру: перед
операцией писать intent, после файлового save фиксировать operation; при
старте сверять незавершённые intent с hash файла и либо завершать, либо
возвращать понятную ошибку. Без такого crash-recovery нельзя объявлять
server `ack` надёжным.

### 5.2. API

Все маршруты требуют JWT и `notes:read`/`notes:edit`; ACL проверяется для
каждой затронутой заметки и целевой папки. Невидимый путь отвечает 404.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/sync/push` | принять пакет локальных операций |
| GET | `/api/sync/pull?cursor=&limit=` | получить упорядоченные изменения |
| GET | `/api/sync/stream` | WebSocket/SSE-сигнал «есть новый cursor» |

```json
// POST /api/sync/push
{
  "deviceId": "b7e5…",
  "operations": [{
    "opId": "d01c…", "kind": "upsert", "path": "Inbox/a.md",
    "content": "# A\n", "baseHash": "sha256:…"
  }]
}
// 200: все применены или уже были применены
{ "acknowledged": ["d01c…"], "cursor": 418 }
// 409: одна из операций конфликтует; непредыдущие операции не применять
{ "code": "conflict", "opId": "d01c…", "path": "Inbox/a.md",
  "contentHash": "sha256:…", "content": "…" }
```

`push` обрабатывает пакет последовательно и атомарно с точки зрения ответа:
либо подтверждает все, либо не подтверждает ни одной. Лимит MVP: 100
операций/1 MiB за запрос. `pull` возвращает только изменения, доступные actor;
cursor продвигается по глобальной последовательности, даже когда изменения
были отфильтрованы ACL, чтобы не зациклиться и не раскрыть число скрытых
заметок.

### 5.3. Web-клиент

`apps/web/src/sync/` — независимый от React модуль:

```text
db.ts        IndexedDB schema and atomic transactions
repository.ts local notes/outbox/cursor operations
engine.ts    push → pull → stream, retry and state machine
types.ts     protocol DTOs only
```

UI получает состояние через hook `useSyncStatus`; редактор пишет сначала в
IndexedDB, а затем ставит операцию в outbox в той же транзакции. В IndexedDB
должны быть `notes`, `outbox`, `sync_state` и `applied_operations` (либо
достаточная дедупликация через cursor). Пользовательский `deviceId` — случайный
UUID из базы, не browser fingerprint.

сначала включается за feature flag `sync.enabled`; включать по умолчанию лишь
после успешной миграции и recovery-тестов.

| `apps/web` | IndexedDB, engine, UI status, i18n en+ru |
| docs | `api.md`, `architecture.md`, ADR, этот план и help-контент |

Не вносить бизнес-логику в handlers и не позволять browser-клиенту самому
менять серверный cursor.

## 8. Риски и меры

- **Crash между файлом и журналом:** intent/recovery из §5.1 и тест на
  принудительное прерывание каждого шага.
- **Одновременное изменение:** в MVP `baseHash` → 409 и UI «оставить моё /
  взять серверное / сохранить копией»; не применять last-write-wins к тексту.
- **Дубликаты и reconnect:** unique `op_id`, pull по cursor, WebSocket только
  wake-up signal; протестировать доставку любого события 0, 1 или N раз.
- **Рост журнала:** snapshot/compaction не делать до появления метрик; сначала
  retention и бэкап SQLite. Перед выпуском установить лимит и alert.
- **Переименование и удаление:** tombstone с UUID заметки; не использовать
  путь как постоянный ID в следующей итерации. В MVP запретить rename при
  pending outbox либо выразить его отдельной операцией и покрыть тестом.
- **Старые браузеры/очищенный IndexedDB:** локальные несинхронизированные
  правки нельзя восстановить после очистки storage; UI должен предупреждать
  при ошибке хранилища, серверные — подтягиваются обычным `pull`.

## 9. Критерии приёмки

1. Правка без сети переживает reload вкладки и после восстановления сети
   появляется в другом браузерном профиле.
2. Повтор одного `push` десять раз создаёт одну запись операции, одну
   серверную ревизию и одно итоговое содержимое.
3. Убитый WebSocket/reconnect не теряет изменение: `pull(cursor)` догоняет
   состояние.
4. Одновременные правки одного файла с разным `baseHash` не перезаписывают
   молча данные; UI получает 409 и предлагает три действия из §8.
5. Пользователь без read ACL не видит путь, контент, событие или факт его
   изменения через любой sync endpoint; `pull` продолжает cursor корректно.
6. Внешняя правка Markdown в vault попадает в последующий `pull` ровно один
   раз; собственная sync-запись не порождает дубль watcher-события.
7. Crash-recovery оставляет сервер либо в старом, либо в новом согласованном
   состоянии и никогда не выдаёт `ack` для потерянной правки.
8. `go test ./...`, `go vet ./...` и `cd apps/web && npm run build` проходят;
   добавлены unit-, integration- и browser-тесты offline/reconnect/conflict.
9. Все новые UI-строки есть в `en` и `ru`; docs/api.md документирует ошибки,
   лимиты и курсорную семантику.

> Сначала исследуй текущие точки записи, watcher, историю, API и конфигурацию.
> Создай ADR-006 с конкретным решением для sync journal и crash recovery.

отдельного review.
