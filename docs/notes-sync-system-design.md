# System design: offline-first заметки и синхронизация

## Цель

Сервис должен работать как приложение заметок на iPhone: пользователь может
создать или отредактировать заметку без сети, изменение сразу сохраняется на
устройстве и затем автоматически появляется в вебе и на остальных устройствах.
Первым клиентом является web-приложение, но протокол и модель данных одинаковы
для будущих iOS, Android и desktop-клиентов.

Это не синхронизация файлов по принципу «последняя версия файла победила».
Это синхронизация операций над заметками: каждое устройство сначала надёжно
сохраняет локальную операцию, а сервер принимает её идемпотентно и рассылает
другим устройствам.

## Что видно пользователю

1. При вводе текст сохраняется в локальную базу браузера/приложения с
   debounce 300–800 мс. Индикатор сразу показывает «Сохранено на устройстве».
2. При наличии сети клиент отправляет накопившиеся операции. После ответа
   сервера — «Синхронизировано».
3. Открытое на другом устройстве приложение получает изменение через
   WebSocket; закрытое — подтягивает его при следующем запуске.
4. При одновременном редактировании текст объединяется без потери обоих
   изменений. Для полей, которые нельзя объединить (например, название),
   применяется детерминированное правило и интерфейс показывает конфликт, если
   это важно пользователю.

«Сохранено» и «синхронизировано» — разные состояния. Нельзя сообщать об
успешной синхронизации, пока сервер не подтвердил операцию.

## Границы первой версии

| Возможность | MVP | Позже |
| --- | --- | --- |
| Текст, заголовок, папки, теги | да | — |
| Офлайн-редактирование | да | — |
| Несколько устройств одного пользователя | да | — |
| Вложения | очередь загрузки, ссылка в заметке | дедупликация, фоновая загрузка |
| Совместные заметки | нет | ACL и обмен ключами |
| Сквозное шифрование | опциональный режим после MVP | включать по умолчанию после recovery UX |
| История и откат | серверные ревизии | UI восстановления и retention-политика |

## Архитектура

```text
Web / iOS / desktop client
  ├─ editor → local database (IndexedDB / SQLite)
  ├─ durable outbox ── HTTPS sync API ──┐
  └─ WebSocket ← live change events ────┤
                                        ▼
                            Sync API + authentication
                              ├─ operation log (append-only)
                              ├─ materialized note state
                              ├─ attachment object storage
                              └─ change stream / WebSocket fan-out
                                        │
                                        └─ PostgreSQL + backups
```

Сервер остаётся источником истины для общей истории и выдаёт единый порядок
изменений для каждого аккаунта. Локальная БД — источник истины для работы
конкретного устройства без сети. WebSocket ускоряет доставку, но не является
гарантией: после reconnect клиент всегда делает `pull` по курсору.

Для текущего проекта это новый sync-адаптер и API: бизнес-правила заметок
остаются в `packages/core`, HTTP и WebSocket — только транспорт, а клиентский
sync-движок не зависит от React. Файловый vault можно оставить экспортом или
локальным источником для single-user режима, но не следует использовать его
как журнал распределённой синхронизации: файловая запись не сохраняет
намерение пользователя и плохо разрешает параллельные правки.

## Данные

### На устройстве

`notes` хранит материализованное текущее состояние, `outbox` — ещё не
подтверждённые операции, `sync_state` — курсор последнего применённого события.
Все три обновляются одной транзакцией IndexedDB/SQLite. Операция никогда не
исчезает из `outbox` до серверного `ack`.

```text
Note: id, owner_id, title, body, parent_id, tags, deleted_at, updated_at
Operation: op_id (UUID), device_id, note_id, kind, payload, base_version,
           client_time
Change: account_seq (monotonic), op_id, server_time, applied_operation
```

`op_id` уникален и делает повторную отправку безопасной. `account_seq` —
непрерывный курсор аккаунта; клиент хранит его после успешного применения.
Не использовать часы устройства для порядка операций: они могут быть неверны.

### API-протокол

```http
POST /api/sync/push
{ "deviceId": "…", "operations": [ … ] }
→ { "acknowledged": ["op-id"], "cursor": 418 }

GET /api/sync/pull?cursor=418&limit=500
→ { "changes": [ … ], "nextCursor": 431, "hasMore": false }
```

Подключение к `GET /api/sync/stream` передаёт лишь сигнал о новом курсоре.
После него клиент вызывает `pull`; так reconnect, дубли и пропущенные сообщения
не меняют корректность. API требует пользователя из JWT и в каждой операции
проверяет ACL к заметке/папке. Идентификатор устройства создаётся при первом
запуске, а не берётся из браузерного fingerprint.

## Алгоритм клиента

При запуске клиент открывает локальную БД, немедленно показывает локальные
заметки, затем запускает `push → pull до конца → WebSocket`. При каждом
изменении редактор в одной локальной транзакции обновляет заметку и добавляет
операцию в outbox. При восстановлении сети он повторяет этот цикл с
экспоненциальной паузой и jitter. Повторы допустимы: сервер дедуплицирует
`(owner_id, op_id)`.

При получении remote change клиент:

1. пропускает уже применённый `op_id`;
2. применяет операцию к локальному состоянию;
3. сохраняет новый курсор в той же транзакции;
4. обновляет открытый редактор без перезаписи локальных неподтверждённых правок.

Удаление — tombstone, а не мгновенное физическое удаление. Tombstone
синхронизируется как обычная операция и очищается только после retention-периода
и подтверждения, что все активные устройства прошли этот курсор.

## Конфликты текста

Для богатого или одновременно редактируемого текста рекомендуемый вариант —
CRDT, например Yjs/Automerge: операции коммутативны, офлайн-изменения
сходятся, пользователь обычно не видит диалога конфликта. Сервер хранит и
ретранслирует обновления CRDT, периодически создаёт snapshot; он не обязан
понимать содержимое текста.

Для простого MVP возможны оптимистичные ревизии: `PUT` содержит `base_version`,
а несовпадение возвращает `409` вместе с актуальным текстом. Клиент выполняет
трёхстороннее слияние; если слияние невозможно, создаёт копию «Конфликт …», не
теряя исходник. Однако это заметно хуже CRDT для мобильного офлайна, поэтому
такой режим стоит считать временным.

Структурные поля синхронизируются отдельными операциями: теги — add/remove с
идентификатором операции, перемещение — LWW с серверным порядком, удаление
выигрывает у редактирования (с возможностью восстановить из корзины).

## Безопасность и восстановление

MVP: TLS, зашифрованные диски/бэкапы, JWT, ACL, лимиты размера и частоты,
аудит изменений. Сервер может индексировать и искать заметки.

Опциональный E2EE: клиент шифрует тело заметки и CRDT updates до `push`;
сервер видит только ciphertext, минимальные метаданные и ACL. Ключ аккаунта
нужен на каждом доверенном устройстве; добавление устройства подтверждается
уже доверенным устройством или recovery key. Это отключает серверный полнотекстовый
поиск и делает восстановление пароля невозможным без recovery-механизма —
поэтому не смешивать его с обычным режимом незаметно.

## Надёжность и эксплуатация

* PostgreSQL: уникальный индекс `(owner_id, op_id)`, транзакционная запись
  operation log + состояния заметки + outbox event.
* Отдельный worker рассылает события из transactional outbox — изменение не
  теряется, если процесс упал между записью и публикацией в WebSocket.
* Ежедневные point-in-time backups базы и версионирование вложений; регулярно
  проверять восстановление в отдельном окружении.
* Метрики: размер outbox, sync lag, `push` retries, конфликты, время `pull`,
  число активных курсоров. Не собирать содержимое заметок в логи.
* Нагрузочные сценарии: один пользователь офлайн на двух устройствах,
  дублирование `push`, потеря WebSocket, удаление vs редактирование, миграция
  схемы, частично загруженное вложение.

## Как это соотносится с Apple Notes

Публично Apple описывает пользовательское поведение так: заметки в iCloud
доступны на устройствах с тем же Apple Account, а создание, удаление и правки
автоматически появляются на остальных устройствах; совместные заметки могут
обновляться в реальном времени. Точная внутренняя схема репликации Apple не
публикуется, поэтому её нельзя считать шаблоном реализации. [Apple Support:
синхронизация и совместная работа](https://support.apple.com/en-gb/guide/icloud/mm2d069f7097/icloud)

В обычном режиме iCloud данные шифруются при передаче и хранении, а ключи
доступны Apple для восстановления аккаунта. При включённой Advanced Data
Protection заметки получают end-to-end encryption: ключи остаются на доверенных
устройствах; для восстановления требуется recovery contact или recovery key.
Веб-доступ при этом по умолчанию выключен и временно подтверждается доверенным
устройством. [Apple: обзор защиты данных iCloud](https://support.apple.com/en-ie/102651)

Следовательно, для нашего web-first продукта разумна та же продуктовая модель
«локально сначала, затем автоматически синхронизировать», но с явно выбранным
компромиссом: server-readable MVP ради web-поиска и простого recovery либо E2EE
с onboarding доверенных устройств и ограниченным серверным поиском.

## Порядок реализации

1. Ввести стабильные UUID заметок, ревизии и таблицы журнала операций/cursors.
2. Реализовать sync API, идемпотентность, ACL и post-commit outbox.
3. В web-клиенте добавить IndexedDB repository, outbox и индикатор статуса.
4. Добавить `pull` на запуске/reconnect и WebSocket signal; покрыть
   интеграционными тестами потери и дубли.
5. Выделить sync engine в platform-neutral TypeScript/Rust/Go-модуль либо
   документированный протокол, после чего подключать iOS SQLite-клиент.
6. После стабильного sync — CRDT для текста, вложения, sharing и, при явной
   потребности, E2EE с recovery-дизайном.
